## 2. 작성 규칙

### 2-1. 장 구성

각 기능 장은 아래 7개 절로 구성한다. 해당 사항이 없는 절은 "해당 없음"으로 표기하고 삭제하지 않는다.

| 절 | 제목 | 내용 |
| --- | --- | --- |
| 1 | 적용 범위 | 대상 화면, 대상 계정, 제외 범위 |
| 2 | 정의 | 장 안에서만 쓰는 용어. 공통 용어는 3절 참조 |
| 3 | 요건 | 핵심 규칙(요건 ID 부여)과 일반 규칙 |
| 4 | 절차·상태 전이 | 처리 순서, 상태 전이표, 판정 조건 |
| 5 | 예외·실패 | 중복 실행, 외부 연동 실패, 삭제·복구, 한도 초과 등 |
| 6 | 연계 | 타 장·타 시스템과의 입출력, 요건 ID 교차 참조 |
| 7 | 미결 사항 | 확인 필요 항목(OI-ID), 확인 대상, 확인 시 판단 기준 |

### 2-2. 요건문 규격

요건은 `조건 → 주체 → 행동 → 결과` 순서의 단문 1개로 쓴다.

| 표기 | 의미 |
| --- | --- |
| ~한다 | 시스템 또는 사용자가 반드시 수행한다 (의무) |
| ~하지 않는다 | 수행하지 않는다 (금지) |
| ~할 수 있다 | 선택적으로 수행할 수 있다 (허용) |
| ~할 수 없다 | 수행이 차단된다 (불가, 시스템이 막는다) |

- 하나의 요건문에는 하나의 규칙만 담는다. 조건이 둘 이상이면 요건을 나눈다.
- 다음 표현은 쓰지 않는다. `적절히`, `빠르게`, `최대한`, `필요 시`, `자동으로`(주체·시점 없이 쓰는 경우). 수치, 시점, 조건으로 바꿔 쓴다.
- 확정되지 않은 내용은 요건으로 쓰지 않고 7절 미결 사항으로 옮긴다.
- 서술 순서는 정상 처리, 제한, 예외, 실패 순이다.

### 2-3. 요건 ID (핵심 규칙에만 부여)

- 형식: `{영역 코드}-{기능 코드}-{3자리}` 예: `A-FEE-014`
- 요건 ID에는 요건명을 함께 쓴다. 요건명은 규칙의 주제를 나타내는 명사형 12자 내외의 이름이다. 예: `A-FEE-004 이용승인 계정의 전이 범위`
- 요건명은 같은 파일 안에서 중복하지 않는다. 요건 내용이 바뀌어도 요건명이 규칙의 주제와 맞으면 ID와 요건명을 유지한다.
- 요건 표의 컬럼은 `ID / 요건명 / 요건` 3개로 통일한다.
- 부여 대상(핵심 규칙): 상태 전이, 금액·수량·기준일 산식, 접근 차단·권한, 삭제·복구 불가, 외부 연동(PayApp 등) 실패 처리, 집계 기준.
- 부여하지 않는 대상: 화면 문구, 목록 컬럼 구성, 필터·검색 항목, 표시 순서.
- ID는 한 번 부여하면 재사용하지 않는다. 삭제된 요건의 ID는 결번으로 둔다.
- 타 요건 참조는 `→ A-FEE-014 이용승인 계정의 전이 범위` 형식으로 ID와 요건명을 함께 쓴다. 같은 표 안에서 반복 참조할 때는 ID만 쓸 수 있다.
- 각 파일 끝에 요건 색인(ID, 요건명, 위치 절)을 둔다.

### 2-4. 주의 블록

| 블록 | 쓰는 경우 |
| --- | --- |
| 경고 | 되돌릴 수 없는 처리, 결제·환불, 개인정보, 데이터 유실 |
| 주의 | 오처리 가능성, 다른 규칙과 혼동하기 쉬운 지점 |
| 참고 | 규칙의 이유, 예시 (규칙이 아니므로 요건 ID를 붙이지 않는다) |

표기는 인용 블록에 블록명을 굵게 쓴다. 예: `> **경고** 삭제한 데이터는 복구할 수 없다.`

### 2-5. 미결 사항 (OI)

- 형식: `OI-{영역 코드}-{번호}`. 구분은 `개발 확인`, `법무 확인`, `정책 확인`, `후속` 중 하나로 쓴다.
- 각 OI에는 확인 대상(누가 확인하는가)과 확인되면 바뀌는 요건 ID를 함께 적는다.
- 확정되면 해당 OI를 삭제하고 요건으로 옮긴다.

### 2-6. 표기 규칙

- 시각이 있는 값의 라벨은 `~일시`, 날짜 단위 값은 `~일`로 쓴다.
- 버튼은 `[버튼명]`, 상태값은 별도 표기 없이 쓴다. 화면 항목명은 화면에 표시되는 명칭과 같게 쓴다.
- 일시·날짜 표시 형식은 디자인시스템 문서의 "날짜·일시 표기"를 따른다.

| 본사 운영제한 | 09SCM 가맹점 이용제한과 같은 제재를 받고, 신규 가맹점 유치가 중단된다 | U-HQ → A-FEE |
| 가맹점 정보 조회 | 09SCM에서 삭제된 가맹점은 목록·지표에서 제외하고 매출·이용료 수납 이력만 합계에 남긴다 | U-FR → A-FEE |
| 거래/매출 현황 | 09SCM 소매·도매 매출조회와 산식·기준일이 동일하다 | U-TRD → R-ORD, W-ORD |
| 공지사항 | 0SCM에서 작성한 09SCM 공지는 본사·가맹점 관리자에 노출된다 | U-SYS → A-NTC |

## 5. 작성 예시 (규격 확인용)

아래는 `09SCM관리자_가맹점이용상태이용료정기결제_정책정리안` 2-2절(이용상태 전이)을 본 규격으로 쓴 예시다. 01~04 파일은 같은 방식으로 작성한다.

### 가맹점 이용상태 전이 (A-FEE)

**3. 요건**

| ID | 요건명 | 요건 |
| --- | --- | --- |
| A-FEE-001 | 이용대기 계정 생성 | 가맹 신청이 접수되면 시스템은 가맹점 계정을 이용대기로 생성한다 |
| A-FEE-002 | 이용상태 변경 경로 | 본사는 이용상태를 가맹점상세의 전이 버튼으로만 변경할 수 있다. 가맹점 목록에서는 변경할 수 없다 |
| A-FEE-003 | 이용대기 계정의 전이 범위 | 이용대기 계정은 [이용승인] 또는 [이용불가]로만 전환할 수 있다 |
| A-FEE-004 | 이용승인 계정의 전이 범위 | 이용승인 계정은 [이용제한]으로만 전환할 수 있다. 이용불가로 직접 전환할 수 없다 |
| A-FEE-005 | 이용제한 계정의 전이 범위 | 이용제한 계정은 [이용승인] 또는 [이용불가]로 전환할 수 있다. [이용불가]는 진행중 주문이 없을 때만 할 수 있다 |
| A-FEE-006 | 이용불가 계정의 해제 | 이용불가 계정은 [이용불가 해제]로 이용대기로만 전환할 수 있다 |
| A-FEE-007 | 이용승인의 PayApp 연동 조건 | PayApp 연동정보의 검증상태가 연동완료가 아니면 [이용승인]을 할 수 없다 |
| A-FEE-008 | 결제실패 시 이용상태 유지 | 정기결제 결제가 실패해도 시스템은 이용상태를 변경하지 않는다. 본사가 결제내역을 확인한 뒤 가맹점상세에서 직접 처리한다 |

**4. 절차·상태 전이**

| 현재 상태 | 가능한 전이 | 조건 |
| --- | --- | --- |
| 이용대기 | 이용승인 / 이용불가 | 이용승인은 PayApp 연동 완료 필요 (→ A-FEE-007 이용승인의 PayApp 연동 조건) |
| 이용승인 | 이용제한 | 없음 |
| 이용제한 | 이용승인 / 이용불가 | 이용불가는 진행중 주문 없음 (→ A-FEE-005 이용제한 계정의 전이 범위) |
| 이용불가 | 이용대기 | [이용불가 해제] |

> **참고** 이용승인에서 이용불가로 가려면 이용제한을 거친다. 계약 종료는 이용제한을 거친 경로로만 처리한다.

위 표에 없는 전이는 제공하지 않는다 (A-FEE-003~006에 포함).
